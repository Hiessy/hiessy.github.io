How we work out the O of a function

Big O describes how a function's work grows with its input. It says nothing about seconds. It answers a more useful question: if the input doubles, what happens to the work?

What the notation says

A function that takes f(n) steps is O(g(n)) if, past some input size, f(n) never goes above a constant times g(n). Constants and smaller terms disappear, so 3n² + 5n + 9 steps is O(n²). For large n, the n² term is the only one that matters.

A worked example

for (int i = 0; i < n; i++) {          // runs n times
    for (int j = i + 1; j < n; j++) {  // n-1 times, then n-2, ... then 1
        if (a[i] > a[j]) swap(a, i, j);
    }
}

The inner line runs (n−1) + (n−2) + … + 1 times, which adds up to n(n−1)/2, or ½n² − ½n. Drop the constant and the smaller term, and that's O(n²).

Recursion

Recursion hides its loops, so we write the cost as an equation called a recurrence: the cost of the recursive calls plus the work around them. Merge sort makes two calls on half the input, then does n work to merge:

T(n) = 2T(n/2) + n

Every level of calls does n work in total, and halving reaches 1 after log₂ n levels. That's n × log n. The Master theorem gives the same answer for any recurrence of the form T(n) = aT(n/b) + f(n), by comparing the work in the calls, n^(logb a), with the work around them, f(n):

Not every recursion fits. Naive Fibonacci calls itself twice and only shrinks n by one, so the calls nearly double at each level. That grows as about 1.62ⁿ.

Best, average and worst

The same code can cost very different amounts on different inputs. Quicksort averages n log n but falls to n² when its pivots are bad, and insertion sort is n on sorted data but n² on reversed data. You can see both above by changing the input in Watch. Unless someone says otherwise, O usually means the worst case.

There's also a floor. There are n! possible orders of n items, and one comparison can at best rule out half of them, so any sort that only compares needs at least log₂(n!) comparisons, about n log n. Counting and radix sorts get below that because they never compare two items.

Why no tool can do this for every function

while (n != 1) {
    n = n % 2 == 0 ? n / 2 : 3 * n + 1;
}

Nobody knows the O of that loop. Nobody has even proved it stops for every n: this is the Collatz conjecture, open since 1937. And it isn't a gap in our tools. A program that always found the O of any code could also decide whether any code stops, and Alan Turing proved in 1936 that no program can do that.

So every tool estimates. This page uses two methods that fail in different ways.

Method 1: read the code

This works on most languages, because loops and recursion look alike in all of them. It removes comments and strings, works out what's nested inside what, checks how each loop's counter moves, and applies the rules above. For recursion it counts the calls, sees how much each one shrinks the input, and solves the recurrence.

It never runs anything, so it can't know what a variable really holds or what an unseen function costs. It can also be fooled by unusual code.

Method 2: run it

This only works for JavaScript, the one language this page can run on anything you paste. The function runs in a background worker at n, 2n, 4n and so on, and we watch what each doubling does to the time:

On a log-log chart, n^k is a straight line with slope k, so the slope of the points estimates the exponent. We then fit each candidate curve to the largest sizes, where small effects matter least, and keep the closest.

This measures real behaviour, including things the first method can't see. It also picks up noise, caches and the compiler warming up, and n and n log n are hard to tell apart. And it only knows about the input it was given, so it can miss the worst case.

    What's left out

    People keep inventing sorting algorithms, so nobody can really implement all of them. These well-known ones aren't here:

    • Block sort (WikiSort, GrailSort): stable and in place, but hundreds of lines each. In-place merge sort shows the same trade-off.
    • Burstsort and multikey quicksort: built for strings, and this lab sorts integers.
    • Polyphase and cascade merge sort: designed for tape drives.
    • Sleep sort: uses timers, so it would measure the clock and not the code.
    • Spaghetti sort: needs actual spaghetti.
    • Stalin sort: deletes anything out of order, which isn't sorting.
    • Quantum bogosort: destroys every universe where the list isn't sorted. Hard to test.

    Timsort leaves out galloping and pdqsort leaves out block partitioning, so neither would match the fastest real versions. Bogosort and friends sit out the race, because they'd never finish it.

    How it's built

    The sorts are written once, in a plain subset of Java. TeaVM compiles them to WebAssembly, and a small script translates the same source to JavaScript line by line, so the race compares two runtimes running the same logic. A test runs every algorithm on 31 sizes and 8 input shapes, in real Java and in Node, and checks each result against the built-in sort and against the other language: 28,336 cases, no mismatches.
