React: when effects run

Events change state, state causes renders, renders run effects. The dependency array is a filter, not a trigger.

MomentDeps comparedLogged
Mountfirst renderstart A
Re-render, still A["A"] vs ["A"]: samenothing
A → B["A"] vs ["B"]: changedstop A, then start B
Unmount-stop B

Steps in order

  1. Props or state change → component re-renders.
  2. React commits the DOM, the browser paints.
  3. React compares each dependency with the previous render (Object.is).
  4. Changed → run the previous effect's cleanup, then the new effect.
  5. Unmount → run the last cleanup.

The cleanup is a closure: it remembers the values from the render that created it, which is why it says stop A.

Flexbox alignment

Find the direction first. justify-content = main axis, align-items = cross axis. Values say start and end, never top or bottom.

.box {
  display: flex;
  flex-direction: column;     /* main axis → vertical   */
  justify-content: flex-end;  /* main axis: bottom      */
  align-items: center;        /* cross axis: middle     */
}
  • row (default): main horizontal, cross vertical. column: the other way round.
  • Values: flex-start, center, flex-end; justify also has space-between / space-around / space-evenly.
  • align-content only acts on wrapped lines; single items use align-items.

Idempotent POST

The client generates the key once per action; the server looks it up and replays the stored response.

  1. User taps Submit → app generates a UUID once.
  2. POST /claims with Idempotency-Key: 9b2f….
  3. Server has no record → creates claim 555 → stores key → 201, Location: /claims/555.
  4. Response lost; app retries with the same key.
  5. Server finds the key → creates nothing → replays the same 201 and Location.

Idempotency-Key goes in the request; Location comes back in the response and holds the server's id, not the UUID.

HashMap keys

get recomputes the hash from the key's current fields. Mutate a key after put and the entry becomes unreachable.

  1. Call key.hashCode() now.
  2. Pick the bucket from that hash.
  3. Compare the stored hash, then call equals.
  4. Both match → value; otherwise null.

Equal objects must have equal hash codes. Keys should be immutable: final fields or a record.

@Transactional and self-invocation

The proxy does the work, not the annotation. A call through this never reaches the proxy.

  1. Controller → proxy.approveAll(): not transactional, just forwarded.
  2. approveAll calls this.approve(7): self-invocation, no transaction.
  3. Each repository call commits on its own; the exception rolls nothing back.

Fix 1: @Transactional on approveAll → all or nothing. Fix 2: move approve to another bean → one transaction per item.

Lost updates

count++ is a read-modify-write, not atomic. volatile gives visibility, never atomicity.

Fixes: AtomicInteger.incrementAndGet() (lock-free CAS), a synchronized method, or LongAdder under heavy contention.

How the JVM runs Java

Compile once to bytecode, interpret it at first, then JIT-compile the hot parts to machine code.

Steps in order

  1. javac compiles .java to bytecode in .class files (platform-independent).
  2. The class loader loads classes lazily, on first use (bootstrap → platform → application loaders, parent first).
  3. The bytecode verifier checks the code is type-safe before it runs.
  4. The interpreter runs bytecode straight away; the JVM counts how often each method and loop runs.
  5. Hot code goes to the JIT compiler: C1 (fast, light optimisation), then C2 (slower, aggressive: inlining, escape analysis). This is tiered compilation.
  6. If an optimistic assumption breaks (say a new subclass gets loaded), the JVM deoptimises back to the interpreter and recompiles later.

Why Java "warms up": the first requests run interpreted; after thousands of calls the hot paths are native code. One reason the readiness probe waits.

Java garbage collection

The GC frees objects no longer reachable from GC roots. Most objects die young, so the heap is split by age.

Steps in order (a generational collection)

  1. New objects go into the young generation (Eden).
  2. Eden fills → minor GC: mark what is reachable from GC roots (stack references, static fields, live threads).
  3. Survivors are copied to a survivor space; the rest is freed in one go (cheap).
  4. Objects that survive several collections are promoted to the old generation.
  5. Old generation fills → major / mixed GC, more expensive.
CollectorWhen to name it
G1Default since Java 9. Heap in regions, aims for a pause-time target (-XX:MaxGCPauseMillis).
ZGCSub-millisecond pauses on huge heaps; generational since Java 21.
ParallelBatch jobs: best throughput, longer pauses.
SerialTiny heaps, one core, small containers.

Stop-the-world pause: application threads halt while the GC works. A Java "memory leak" is an object still reachable but no longer needed: a growing static Map, a cache with no eviction, a ThreadLocal never cleared in a pool, or today's unreachable mutable-key entry.

How a JavaScript engine runs code (V8)

Same idea as the JVM, but starting from source: parse, run as bytecode, JIT the hot functions using the types it has seen.

Steps in order

  1. The browser (or Node) hands source text to V8.
  2. The parser builds an AST; functions not called yet are only pre-parsed (lazy parsing).
  3. Ignition, the interpreter, compiles the AST to bytecode and runs it, recording the types it sees (type feedback).
  4. Warm functions go to Sparkplug / Maglev (quick compilers); hot ones to TurboFan, the optimising JIT.
  5. TurboFan assumes the types stay the same. Pass a string where it always saw numbers and it deoptimises back to bytecode.

Hidden classes (V8 calls them maps): objects created with the same properties in the same order share a shape, so property access becomes a fixed offset, cached by inline caches. Adding properties in different orders, or using delete, changes the shape and slows access.

JavaScript memory

No manual freeing: the engine collects whatever is no longer reachable. Leaks come from references you forgot to drop.

  • Stack: call frames with primitives and references. Heap: objects, arrays, functions, closures.
  • Mark-and-sweep: mark everything reachable from the roots (globals, the current stack), free the rest. Cycles are fine, unlike reference counting.
  • V8 is generational too: a fast scavenger for the young generation, mark-compact for the old one, mostly concurrent and incremental so frames don't stutter (the GC project is called Orinoco).
  • A closure keeps the variables it uses alive as long as the function itself is reachable.

Classic front-end leaks

  1. Event listeners or setInterval never removed. In React: the missing effect cleanup.
  2. Detached DOM nodes still referenced from a variable or array.
  3. Ever-growing global caches or arrays.
  4. Closures holding large objects (a big response captured by a long-lived callback).

Find them in Chrome DevTools: Memory panel → take a heap snapshot, compare two, look for "Detached" nodes.

The event loop

JavaScript runs your code on one thread. I/O is handed off, and callbacks wait in queues until the call stack is empty.

Steps in order (one turn of the loop)

  1. Run the current script or task until the call stack is empty.
  2. Run all microtasks: promise callbacks (.then, code after await), queueMicrotask.
  3. The browser may render (style, layout, paint; requestAnimationFrame callbacks run just before).
  4. Take one task (macrotask) from the queue: a setTimeout callback, a click, a network event. Run it.
  5. Back to step 2.
console.log("1");
setTimeout(() => console.log("4"), 0);          // task
Promise.resolve().then(() => console.log("3")); // microtask
console.log("2");
// prints 1, 2, 3, 4: microtasks run before the next task, even a 0 ms timeout

Java contrast: Java runs many threads on many cores with shared memory, so it needs locks and atomics (today's lost-update question). Plain JS on one thread can't hit that race; Web Workers add threads, but they share nothing by default and talk by messages.
